Table-Video SOP 是一套公开的视频制作资料包：它把“文案和配音已经定下来之后”的工作，拆成编码 Agent 可以照着执行的规则、模板和提示词。它来自抖音作者一只桌子的实际制作与返工，公开在 GitHub 仓库 Table-VideoSOP，默认技术路线是 Remotion 加 FFmpeg，配合能读写本地文件的 Agent 使用。[1][2]

如果你做的是科普、观点讲解或产品演示这类以人声解说为主线的视频，希望画面由 AI 参与生成、又能分段并行推进，这套资料包想解决的就是“怎么把一件事交代清楚，让 Agent 每次都能按同一套规则做”。分工在开头就划清了：你负责内容、风格和采用决定，Agent 负责规划、任务准备、动画与后期、检查和记录；生图和生视频由你在选定的工具里手动完成。[2]

<!--more-->

## 主题概览

这套流程的前提和一般“一句话出片”很不一样：它假设你已经确认了文案，并录好了配音，之后所有画面、音效和字幕都以这条配音的时间为基准来排。[2] 作者在文字版里也写明，他的做法离全自动出片还很远——画风定成什么样、设计图过不过、哪一版能用，都要人拍板。[13]

资料包本身是“方法”而不是“成品工程”：仓库不含 demo、制作工程、生成服务和角色素材，只提供 SOP 文档、规则、经验文件、模板和可复制的提示词。默认介绍 Remotion 与 FFmpeg 路线，也可以在保持相同输入、确认和验收要求的前提下换成别的工具。[2]

## 核心技术

### 三份文件把顺序、路由和外观分开

项目里长期维护三类文件：SOP 写制作顺序，`AGENTS.md` 负责任务路由，`DESIGN.md` 描述画面长什么样、该怎么动。每一期再另有一份制作大段表，记录本期的分段、采用版本和进度。[2]

`AGENTS.md` 是一个开放的 Markdown 约定，作为“给 Agent 看的 README”使用，Codex、Jules、Cursor 等一批编码 Agent 都会读取它，项目规模大时还能在子目录里各放一份、由最近的生效。[8] 在这套流程里它承担两件事：一是路由，告诉 Agent 做某类任务前该先读哪份经验（涉及录屏剪辑就先读录屏经验，涉及全片拼接与音效就先读声音和字幕的验收经验）；二是把容易漏的检查点写成条目，例如做 Remotion 动画时记下关键动作的时间戳，最后配音效才对得准。[2][13]

`DESIGN.md` 用的是 Google Labs 提出的格式规范：YAML front matter 放机器可读的设计 token（颜色、字体、间距、组件），正文写人可读的取舍理由，官方还提供了 CLI，可以检查结构、token 引用和 WCAG 对比度。[9] 放在这套流程里，它就是把“这一系列片子的视觉和运动语言”一次写清，之后每次让 Agent 出设计图、做动画都按它来。

### 配音是时间基准，大段表决定画面补什么

整套流程以最初定下的配音为基准。大段表不按固定秒数或“一句一镜”切分，而是按叙事任务、视觉关系、技术路线或风险变化划段，每段要回答三件事：这段配音已经说了什么、画面必须新增配音里没有的哪些信息、屏幕上真正需要留下的文字是什么。[2]

作者反复强调的一点是，画面用来增强配音表达，而不是把台词再复述一遍；如果整段画面只是把配音文字再打一遍、让字飞来飞去，那和做个 PPT 没什么区别。[2] 实践中“画面必须新增”那一列通常最难写，也是后面返工最多的来源。[13]

### 动画、剪辑和录屏各用一件工具

| 工具 | 定位 | 在这套流程里的角色 |
| --- | --- | --- |
| FFmpeg | 跨平台命令行音视频处理工具 [3] | Agent 通过代码完成剪辑、拼接、合成 |
| Remotion | 用 React 组件描述画面，官方给编码 Agent 提供了 Skills 安装方式和 Remotion Studio 预览 [4] | 默认动画路线，承担复杂运镜与景深 |
| HyperFrames | HeyGen 开源的 HTML + GSAP 视频框架，用 Puppeteer 与 FFmpeg 做可跳转的页面转视频渲染 [5] | 备选动画路线 |
| ChatCut | 对话式剪辑，指令落到真实多轨时间线上，之后仍可手动调整 [6] | 剪配音、出字幕 |
| Recordly | 开源的录屏与演示录制工具，自带自动缩放和光标平滑 [7] | 录屏素材 |

选型上的判断来自作者自己的使用感受而非通用排名：他说 Remotion 在动画精修、复杂运镜和景深上比 HyperFrames 更强，此前有一期视频用的是 HyperFrames，其余各期都用 Remotion。[13] 他不用 ChatCut 做图形动画，因为插件里做不了真正的三维摄像机动画，高级一点的功能还要额外付费；在他看来它最有价值的是那条可视化时间线，所以只拿它剪配音和出字幕。[13] 这与 ChatCut 官方对自己的描述一致：说想怎么剪，改动就落在真实轨道上，之后每一处都能手动调整。[6]

用 Remotion 之前值得先看清许可：它对个人、3 人及以内的公司、非营利组织免费，团队规模超过之后需要购买公司许可，源码公开不等于任何规模都能免费商用。[11]

生图和生视频这两步作者是手动做的：图在 ChatGPT 网页端生成，视频用 Google Flow，主要出于成本考虑。[13] Flow 是 Google 为 Veo、Imagen 和 Gemini 打造的 AI 影视工具，能按素材保持角色与场景一致性。[10]

### 先把设计规则测出来，再开始做片子

动工前的第一件事不是做视频，而是用两轮测试把设计规则定下来。静态测试比较背景色、卡片倒角、字体和 IP 角色放进画面后的协调度，直接让 Agent 出设计图、用眼睛对比；动态测试看图形怎么变换、图形之间怎么互相影响（比如小球撞上去，被撞的图形有没有受力带动的感觉）、跟随和次要运动、以及运动时的挤压与拉伸。[2]

动态测试的关键词是“迪士尼动画十二原则”——蓄力、跟随与重叠动作、慢入慢出、挤压与拉伸这类运动规律。它们最早由迪士尼动画师在实践中总结，1981 年由 Frank Thomas 与 Ollie Johnston 整理成书，后来也一直适用于电脑动画。[12] 跟 Agent 说按这套原则来，它就能理解。两轮测试都满意后，让 Agent 把结果写成 `DESIGN.md`，作为整个系列的风格基准。[2]

流程里还留了两处刻意的人工关卡：每段的镜头剧本和设计图要先给人审，确认后才开始做视频；只有确实没做过的新做法（新的镜头方式、空间处理、角色互动或转场）才先做一段带配音的样片，同类段落直接对标已经确认过的片子。[2] 作者的账算得很直接：跳过设计确认直接产出成片，后面一旦要大改，token 消耗会顶不住。[13]

为了让最后的音效对得上，动作标注要按镜头起点 `00:00.000` 为基准，写清触发、开始、接触或碰撞、状态变化、结束和停稳的时间；单次音效写成精确秒点（例如 `SFX @ 00:01.250`），持续声音写起止区间，并注明声源和对应动作。[2][13]

## 实践应用

资料包的 README 按九个步骤给出了可以直接复制的提示词，从初始化项目一直到封面与发布材料。[2] 下面是缩略后的实际操作顺序：

1. **初始化**：把资料包放进自己的系列目录，用能读写本地文件的 Agent 打开该目录。第一次对话作为总控，负责整期规划、采用记录和总装；后续分段对话只管各自的任务。这一步填好制作路线（默认 Remotion＋FFmpeg）、协作方式和已有素材路径，只检查路径、工具、版本与权限，不安装东西。[2]
2. **建立风格基准**：完成静态与动态两轮测试后，从选中的样本里提取配色、字体、布局和运动参数，整理成 `DESIGN.md`；没测过、没确认的部分写“待定”，不把静态确认当成动态也确认了。[2]
3. **每期开工**：确认稿件与配音，核对语义范围、停顿和配音文件是否可用；出制作大段表并确认划段、路线与分工；按模板一次写完镜头剧本；再按分段准备目录和开工指令，逐段推进。[2]
4. **组装与交付**：各段成果经采用确认后接入唯一主工程，生成审片文件检查语义、可读性、段间衔接和遮挡；画面锁定后再处理音效、字幕，最后做封面与发布材料。[2]
5. **回写经验**：整期交付后做一次复盘，用原话记录返工，并区分是“规则没写”还是“写了没执行”，把满意的画面记为以后的对标片。[2]

一条典型的推进顺序是：

```text
确认稿件与配音 → 制作大段表 → 镜头剧本（人工审） → 分段设计图（人工审）
→ 分段制作 → 全片视觉确认 → 总装 → 音效与字幕 → 封面与发布材料
```

判断每一步是否真的做完，资料包给的是可检查的判据，而不是“看起来不错”：本期目录和工具可用性要有实际证据；`DESIGN.md` 要能定位到采用的样本、参数可执行；每段要有负责人、输入、设计交付和依赖；配音与稿件相符，因为“有音频文件”不等于时基已经核对过。[2]

### 需要先看清的边界

**这套资料包的自查范围有限。** 仓库说明写明，主要路由只在 Windows 与 Codex 环境下、用不继承原对话的任务检查过并据此修订；镜头只在窗口框内移动的问题在测试后补了规则但尚未复测，全新电脑安装、完整视听成片和视觉质量的独立复现都还没有做。[2] 因此它更适合当作一套可修改的方法起点，而不是开箱即用的成品工程。

**时间线定下来之后就不好改。** 流程以最初的配音为基准，后期虽然也能小改配音，但不如在剪映、PR 里直接拖时间线方便：时间线一动，后面的动画、音效和字幕都要重新对齐，相关画面还要重新渲染。[13] 所以它适合在确定好的时间线上做内容，不适合频繁调整剪辑结构。作者也在试让 Computer Use 操作剪映、达芬奇这类剪辑软件，但认为远没有营销号说的一句话出片那么简单，而且 Windows 下 Computer Use 不能后台操作。[13]

**许可和素材要分开看。** 仓库说明正文、模板、提示词与文字示例采用 CC BY 4.0，复制、修改和商用需要署名、附许可链接并说明是否改动；`tools/` 下的脚本是 MIT；`assets/` 下的封面与截图（含作者的角色形象）保留所有权利，不在上述许可范围内。[2] 第三方内容按各自许可处理。
