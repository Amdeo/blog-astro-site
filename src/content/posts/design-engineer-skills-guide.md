[emilkowalski/skills](https://github.com/emilkowalski/skills) 是一套给编程助手用的技能包：作者 Emil Kowalski 把自己判断「什么算好界面」的经验写成一份份 `SKILL.md`，让 agent 照着执行。他的判断来自在 Vercel 和 Linear 做设计工程的经历。

它解决的不是「AI 不会写界面」，而是「AI 总在细节上选错」：入场动画该用 `ease-out`，它用了 `ease-in`；该用半透明阴影的地方，它放了个实心边框。这些错单独看都不影响功能，叠在一起界面就始终差一点。

<!--more-->

这个「差一点」可以写成明确约束。比如入场时先快后慢，用 `ease-out` 让反馈及时出现，再平稳停下。[《Agents with Taste》](https://emilkowal.ski/ui/agents-with-taste)里的思路值得借：别只要求「有品味」，把自己为什么选择这条曲线、为什么删掉某个动效说清楚。

这套技能还有一条不太显眼的原则：会拒绝。`find-animation-opportunities` 明写「期望拒掉大多数候选」，整个应用最多给 5 到 7 条建议——一份高置信的短清单比一张长愿望单值钱。它的目标不是让界面到处都在动。

## 最值得看的一份：apple-design

它把 Apple 的 WWDC 公开设计内容转成 Web 场景的实现建议：动画从当前屏幕状态开始，继承手势速度，松手后自然收束，并且随时能被抓住改向。它是社区整理的技能，不是 Apple 官方发布。

最硬的一条是可中断：任何动画都要能在任意时刻被打断改向。用户能抓住飞行中的元素推回去，而不用等它播完；转场期间也不能锁住输入。这一条直接否掉了很多「关掉再重开」的写法。

弹簧也不是越弹越好。普通状态切换先求稳定；拖动、甩动这类带速度的手势，再考虑适量回弹。拖拽面板时，松手速度影响最后吸附的位置，拉到边界后阻力逐渐增加，比直接硬停更能说明「这里已经到头了」。

## 主体技能的四条硬规则

`emil-design-eng` 是入口，写动画代码之前先回答两个问题：这个动画多久会被看到一次，谁触发。由此得到几条能直接执行的：

- 高频操作少做动画，避免让用户一遍遍等同一段过渡。
- 键盘触发优先即时反馈，而不是追求展示效果。
- 常规 UI 过渡尽量短，不轻易用起步慢的 `ease-in`。
- 需要连续拖动与中途改向时，优先考虑能继承速度的弹簧，而不是反复重启动画。

这些是这套技能的默认取舍，不是所有产品都必须遵守的物理定律。真正要回答的仍然是：动画有没有帮助用户理解变化，有没有拖慢操作。

审查类技能则把标准前置：默认就是挑问题，通过是要挣来的，每条动画都得回答「为什么要动」，结论按 Before / After 表格输出，方便复核。

## 先审，再改

其中一些技能专门找机会、提改进建议，并要求先报告、不直接改源码。这个分工很实用：先让助手指出最值得改的几处，再决定是否实施，不必接受一份覆盖全站的动效改造清单。

改进计划要能独立执行。与其写「弹窗更自然一点」，不如指出哪个文件、哪段过渡、从什么状态到什么状态、何时允许中断，以及怎样判断改好了。这样换一个执行者，也不用重新猜一遍设计意图。

## 装与验

```bash
npx skills@latest add emilkowalski/skills
```

安装时选自己的编程助手与作用范围；也可以先读一份技能，把其中的要求用于一次小范围审查。

验证不是看装没装上，而是让它做一件具体的事：审一段刚写的弹窗动画，看结论里有没有具体曲线、时长和 `transform-origin` 的判断。技能文件是写给模型看的规则，规定「应该怎么做」，不保证每次都遵守；拿一个小的真实改动试一次，比读十遍 README 有用。

我更看重它把设计判断落到具体改动上的方式：不是让页面到处动，而是能说清每个动效为什么存在，以及什么时候应该删掉它。
