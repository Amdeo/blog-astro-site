AI 把一个小功能写成一套框架，确实值得约束。但如果约束变成“行数越少越好”，输入校验、兼容处理和测试也可能一起被删掉。评估这类插件，应该先问：它减少的是不必要的实现，还是必要的工程工作？

Ponytail 是给编码代理加载的规则与适配插件，不是新的模型。它希望代理先查项目已有能力，再决定是否增加代码，并保留验证、错误处理、安全与可访问性约束。[1][2] 这篇文章讨论规则怎样起作用，以及怎样读它的实验数字，不把项目方报告写成自己的实测。

<!--more-->

## 规则改变的是决策顺序

本次核对的 `skills/ponytail/SKILL.md` 要求代理先读任务和受影响代码，找到调用方、测试、夹具、配置与导出，再选择满足需求的最小改动。它给出的优先顺序包括复用代码库能力、标准库或平台能力、已装依赖，最后才写新实现。[2]

一个容易忽略的限定是：**项目已经有统一组件时，项目约定优先于原生控件。** 规则原文就写着 “A house component beats a native widget”。[2] 因此，“浏览器有日期输入框”不能自动推出“应该删除项目的 DatePicker”。统一组件可能还承担键盘操作、错误反馈和设计约束；是否可以替换，要回到实际需求检查。

同一份规则还要求：非平凡的新逻辑留下小测试或断言自检，移动代码时保留已有错误处理，不删除信任边界校验和防止数据丢失的处理。[2] 简化的是解决方案，不是把检查步骤一并省掉。

这些约束仍需要宿主正确加载，也需要代码审查验证是否遵守。规则文件里写了某条要求，不等于代理每次都能做到。

## 先把基准的两组任务分开读

下面专门核对旧文引用的 **2026-06-18 报告**，而不是把它当成当前 Ponytail 5 的性能结论。当前 README 已经指向另一轮模型、任务和运行次数不同的实验，两轮数据不能混着比较。[1][4]

六月报告使用 Claude Code `2.1.177`、Haiku 4.5，以及固定提交的 FastAPI + React 模板。每个任务、每个对照方案运行四次。[4]

**第一组是 12 项功能任务。** 项目方报告 Ponytail 相对无技能基线：新增代码行数减少 54%、tokens 减少 22%、成本减少 20%、时间减少 27%。但代码量统计是 `git diff` 的新增行数，报告明确说这部分没有启动服务或浏览器。它能说明生成规模与运行消耗的变化，不能单独证明功能质量相同。[4]

**第二组是安全相关函数检查。** 报告的 safe-rate 表给出 Ponytail 为 `20/20`，而简短 YAGNI 提示对照为 `19/20`。这是预设对抗输入上的通过情况，不是“生成代码具有 100% 安全性”。作者也明确提醒：确定性检查不是安全性的证明。[4]

报告自身还有一个需要保留的疑点：安全轴标题和限制章节写“6 tasks”，safe-rate 表却按“五项安全任务 × 四次”统计。仅凭正文不能消除这个口径差异。因此本篇分开转述两组结果，不再把功能收益和安全通过率拼进同一行，更不据此给跨模型的可靠性排名。[4]

## 峰值收益不能直接变成选型结论

六月报告里，日期选择器从基线平均 `404` 行降到 `23` 行，是把手写组件换成平台能力的场景；搜索接口则四组都约为 `44` 行，几乎没有可压缩空间。[4] 它们说明收益依赖任务，而不是给任何项目加上规则都能按同一个比例省钱。

这类工具更值得放在“代理经常重复造已有能力”的项目里评估。如果问题是接口约定不清、历史兼容复杂或需求经常变化，单靠强调少写代码，无法代替澄清需求和补齐验收。

## 接入路径跟客户端和主版本走

下面是固定来源版本的**安装文档示例，本文没有执行**，也没有修改当前机器的插件或规则配置。[3]

Codex 的插件命令是：

```bash
codex plugin marketplace add DietrichGebert/ponytail
codex plugin add ponytail@ponytail
```

当前 INSTALL.md 为 OpenCode 2 给的是另一条路径：

```bash
opencode plugin add @dietrichgebert/ponytail
```

文档另行说明了 OpenCode 1 的旧配置键与加载方式；不能把上述命令当作所有主版本通用。Codex 的生命周期 hook 也需要审阅授权，不能因为插件名字熟悉就直接信任。[3] 对其他宿主，应看对应安装章节，尤其不要覆盖已有的 `AGENTS.md` 或将另一客户端的命令改个注释就当成适配。

## 在自己的项目里怎样做有效对照

评估时先固定一个能独立验收的小任务，而不是先看总代码量。两组使用相同代码基线、模型与宿主版本、需求和成功标准，再比较：

1. 是否满足相同接口和功能要求，有没有漏掉输入边界、权限、错误处理及可访问性要求。
2. 是否通过同一套已有回归和任务验收，而不只是代理为自己写的测试。
3. 最终 diff 增加了什么依赖、抽象与维护负担，再记录耗时和实际模型用量。
4. 多次运行的变化是否足够稳定，有没有只挑最好的一次展示。

还要隔离全局插件和会话历史。六月报告记录过一次实验污染：hook 意外在基线组也触发，导致“未启用”那组实际受到了规则影响。[4] 如果没有确认两组真正不同，后面的节省比例就没有可解释性。

这是一套评估建议，不是本篇已经执行的对照实验。最终是否采用，应由自己项目的验收和维护成本决定，而不是用项目方峰值数字替代判断。
