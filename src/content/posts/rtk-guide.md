RTK，全称 Rust Token Killer，是一个装在本地电脑上的命令行工具。它把冗长的终端输出整理得更短，再交给 AI 编程助手阅读。[1]

比如你让 AI 修复一个测试报错。AI 要运行测试、阅读结果、改代码，再运行一次。每一轮都可能产生大量日志，而它真正需要关注的，往往只是哪些测试失败、哪里报错。RTK 就是在这个过程中，帮它减少需要阅读的文字。

**它不是新的 AI 模型，也不负责替你写代码。它整理的是 AI 工作时读到的命令结果。** 如果你经常让 AI 在项目里运行测试、查看 Git 或搜索文件，可以了解它；如果只是打开聊天网页问问题，它通常派不上用场。

<!--more-->

## 放进一次修复任务里，就容易理解了

假设你对 AI 说：“这个项目的测试挂了，帮我修好。”

没有 RTK 时，AI 运行测试，拿到原始输出，再从成功记录、提示信息和错误堆栈里找线索。这里的“错误堆栈”，就是程序报错时列出的调用过程。

加入 RTK 后，测试仍然要运行，错误也仍然要修。改变的是结果的呈现方式：对于支持的测试命令，RTK 会把通过的测试合并成数量摘要，把失败项和相关错误保留下来。[1] AI 接着根据这份更短的结果处理问题。

流程可以这样看：

```text
你提出任务 → AI 运行命令 → RTK 整理命令输出 → AI 阅读结果、继续工作
```

所以它压缩的不是项目代码，也不是一个待解压的文件，而是“这次命令执行后，要给 AI 看的那段文字”。

## 除了测试，它还能整理什么

RTK 会按命令类型采用不同的整理方式，不是把所有输出统一砍掉一半。[1]

| 工作中常见的输出 | RTK 怎样整理 |
| --- | --- |
| Git 状态 | 更紧凑地列出哪些文件被修改、哪些尚未跟踪 |
| Git 历史与差异 | 精简提交记录的展示，减少差异输出里的部分上下文和标题 |
| 测试结果 | 将通过项收成摘要，重点展示失败项 |
| 文件搜索结果 | 按文件分组，限制过长的行和过多的匹配结果 |

如果你的 AI 经常反复跑这些命令，RTK 才有比较明确的使用位置。它不会替你决定该运行什么命令，也不会因为一份日志变短，就自动证明代码已经正确。

## 少读这些文字，有什么用

AI 编程助手通常需要把命令结果放进当前对话，才能据此继续工作。模型可读取的上下文有容量限制，输入文字也会计入用量；其中常说的 token，可以先理解为模型处理文字的计量单位。

RTK 想减少的，就是终端输出占用的这部分空间。[1] 对一个要反复测试、搜索、检查代码的长任务，少塞进一些重复内容，可能让有限的上下文用得更久。

但这不等于总费用会按同样比例下降。你的需求、对话历史，以及模型生成的回复也会占用 token，终端日志只是其中一部分。[1] 更不能据此承诺 AI 修得更快、更准。

## 怎样先试一把

不必一开始就把所有自动集成都配好。先手动比较一条熟悉的命令，更容易判断它对你有没有用。

macOS 用户如果已经使用 Homebrew，可以按项目文档安装；已经装好则跳过安装这一行：[1]

```bash
brew install rtk
rtk --version
```

接着进入一个本地 Git 项目，分别运行：

```bash
# 原本的 Git 状态输出
git status

# 经过 RTK 整理后的输出
rtk git status
```

不用先研究一堆统计指标。看两件事就够了：**文字是不是更短了，你关心的修改文件是不是仍然能找到。** 如果项目本来就没多少输出，差别也可能很小。

排查问题时，如果想重新看完整的原始输出，可以用：

```bash
rtk proxy git status
```

这里的 `proxy` 表示跳过整理、直接执行原命令。[1] 不需要卸载 RTK，也不用改项目。

## AI 会自己用上它吗

**只装好 RTK，不代表 AI 就会自动使用它。** 前面的手动用法，是你自己把 `git status` 写成 `rtk git status`。

若想让 AI 在工作时自动经过 RTK，还需要按所用编程助手完成对应接入。接入的作用，是把助手准备运行的命令转成 RTK 的形式，让它收到整理后的结果。[1]

这一步与“安装了一个命令行程序”是两件事。不同助手的接法不同，应该看项目 README 中对应的安装章节，不必照抄一整张客户端命令表。

另外，某些助手直接用自己的内置工具读文件、搜索代码。这些调用不一定经过终端，也就未必会用到 RTK。[1] 因此，装完之后不能假设所有信息都会变短。

## 实际能变短多少

下面是我用本机 RTK 0.51.0，在一个临时 Git 项目里的比较。数字单位是字节，可以理解为输出文本的大小，不是模型 token 数：

| 同一条命令 | 原始输出 | RTK 输出 |
| --- | --- | --- |
| `git status` | 370 字节 | 91 字节 |
| `git diff` | 704 字节 | 439 字节 |
| `git log` | 965 字节 | 354 字节 |

这个小实验说明它确实可能缩短常见 Git 输出，但不是任何场景都有同等收益。同一轮里，两条短小的搜索输出经过 RTK 后就没有变短。

所以，比起先相信一个最高节省比例，更实用的办法是拿自己项目里最常出现的几类输出试一遍。

## 要不要放进自己的工作流

如果你经常使用能操作终端的 AI 编程助手，而且一个任务里要反复运行测试、检查 Git、搜索文件，RTK 值得先小范围试用。

如果你只是偶尔问 AI 一个问题，或者任务输出本来很短，就没必要为了“省 token”先加一层工具。

最后保留一个习惯：**摘要用来快速定位，原始输出用来查细节。** 尤其在排查复杂错误或审查代码差异时，不要只凭精简后的结果下结论。项目设计中也保留了过滤失败时回退原始输出的路径。[2]
